| **Recall@K 计算** | `metrics_retrieval.py#L16-L30` | `hits = sum(1 for cid in deduped[:k] if cid in golden_chunk_ids)`<br>`return round(hits / float(len(golden_chunk_ids)), 4)` | **符合数学定义** |

### 2. 特别核查：BM25 与 Reranker 出现 Recall@1 = 92.5% 与 MRR@10 = 1.0000 的成因剖析

在 E2.1 实验汇总表中，方案 B (BM25) 与方案 D (Reranker) 均输出了：
$$\text{Recall@1} = 92.50\%, \quad \text{MRR@10} = 1.0000$$

表面上看，Recall@1 只有 92.5%，通常容易被直觉误解为“有 7.5% 的题目首位没命中，为什么首位倒数排名均值 MRR 还能是完美的 1.0000？”

**逐题计算证据与底层数学真相**：

1. **样本黄金分块数量不均衡**：
   - 检查 `benchmark_v1.jsonl`：全量 20 道题目中，**有 17 道题目仅标注了 1 个黄金核心分块**（单事实定位）；
   - 但有 **3 道多跳/多事实题目（Q04, Q17, Q18）标注了 2 个黄金分块**（1 个直接答案分块 `relevance=2`，1 个支撑上下文分块 `relevance=1`）。
2. **在 $K=1$ 截断下的天然物理限制**：
   - 当 $K=1$ 时，系统返回列表 `deduped[:1]` 中**最多且只能容纳 1 个 Chunk**。
   - 对于拥有 2 个黄金分块的 Q04、Q17 和 Q18：
     - BM25 和 Reranker 均精准地将核心直接答案分块排在了 **Rank 1**。
     - 此时，Top-1 里的命中数为 1，但该题黄金分块总数为 2！
     - 因而该题单题的：
       $$\text{Recall@1} = \frac{1 \text{ (hits)}}{2 \text{ (golden)}} = 0.5000\ (50\%)$$
3. **MRR 的计算只看“首个相关分块”**：
   - 因为排在第 1 位的 Chunk 本身就是合法的黄金相关分块，所以对 Q04、Q17、Q18 而言，首个相关分块的排名均为 1！
   - 单题倒数排名 $\text{RR} = \frac{1}{1} = 1.0000$。
4. **全集 Macro Average 算术求和验证**：
   - **Recall@1**：
     $$\text{Macro Recall@1} = \frac{17 \times 1.0000 + 3 \times 0.5000}{20} = \frac{17.0 + 1.5}{20} = \frac{18.5}{20} = \mathbf{0.9250\ (92.50\%)}$$
   - **MRR@10**：
     $$\text{Macro MRR@10} = \frac{17 \times 1.0000 + 3 \times 1.0000}{20} = \frac{20.0}{20} = \mathbf{1.0000}$$

**核查结论**：
数据并非计算 Bug，亦非指标造假，而是**单分块截断与多黄金标注交集下的正常数学必然**。这也提示我们在后续多事实评测中，针对多黄金分块问题应重点关注 $K \ge |G|$ 时的指标（如 Recall@3、Recall@5）。

## 二、实验规模问题审计（严谨技术定性）

审计发现，当前 Benchmark v1 存在明显的**语料规模过小导致评测饱和**的问题：

1. **实际返回候选数与知识库总规模**：
   - 当前评测数据库内经过真实入库的总 Chunk 数为 **16**。
   - 实验配置的 Candidate Pool 为 **20**。
   - 经代码追踪：
     - Dense 检索：16 个分块与 Query 的余弦相似度均大于 0，实际返回了**全部 16 个分块**。
     - BM25 检索：因过滤无字面重合的 0 分分块，平均每题返回 **11.35 个分块**（最少 8 块，最多 14 块）。
     - RRF 混合检索：将 Dense(16) 与 BM25(8~14) 取并集，结果再次覆盖了**全部 16 个分块**。
2. **Reranker 的实际工作面**：
   - 方案 D (Reranker) 接收了 RRF 输出的候选池。在 16 个分块的总量下，Reranker **实际上是对整个知识库进行了全库重排**，而非在数万分块中针对第一阶段召回的 Top-20 进行重排。
3. **Recall@5 = 100% 的失真成因**：
   - 16 个分块中截取 Top-5，截取比例高达全库的 $5 / 16 = 31.25\%$；截取 Top-10 比例高达 $62.5\%$。
   - 在只有 16 块的微型知识库中，只要初筛稍微相关，核心分块极难跌出前 5 名。
   - **客观定性**：当前 Recall@5 = 100% 和 Recall@10 = 100% **严重受到了微型语料规模的保护**，无法真实反映大规模真实生产知识库（数千至数万 Chunk）中第一阶段粗筛召回的“漏网之鱼”与召回失真。

## 三、延迟测试可靠性审计

针对方案 D 中 CPU 环境下 Reranker P50 达到 **1333.78 ms** 的审计分析：

1. **模型冷启动排查**：
   - 代码在正式评测循环前执行了明确的 Warm-up 阶段（`run_retrieval_ablation.py#L125-L131`），预先执行了一次 Embedding、一次 BM25 和一次 ONNX Rerank 推理，因此 **排除了模型加载与 ONNX Session 初始化的冷启动开销**。
2. **延迟高昂的真实物理原因**：
   - 模型采用 `Xenova/bge-reranker-base`（2.78 亿参数，基于 12 层 Transformer 结构）。
   - 在方案 D 中，Reranker 接收了 RRF 传入的全部 16 个分块。
   - 在 CPU（Intel/AMD 多核但无 GPU 加速）上，执行 16 次长度约 300~400 tokens 的 Query-Doc 交叉注意力矩阵计算，分 2 个批次（batch_size=8）。
   - 单次交叉注意力推理在 CPU 上平均耗时约 75~85 ms，16 个分块累计纯推理时间约为 $16 \times 80\text{ms} \approx 1280\text{ms}$。
   - 加上初筛检索与线程切换，端到端耗时集中在 **1300~1400 ms**，完全符合纯 CPU 跑大参数 Cross-Encoder 的物理规律。
3. **当前计时边界的缺陷**：
   - 目前 `run_retrieval_ablation.py` 在 CSV 中仅记录了端到端总时间 `rerank_dt = rrf_dt + rerank_res.duration_ms`。
   - 未在最终产物中把 `t_embedding`, `t_dense_search`, `t_bm25_search`, `t_rrf_merge`, `t_rerank_inference` 细分展示，导致用户无法一眼看清各阶段开销占比。

## 四、实验结论深度反思与重新分析

### 1. 为什么当前 BM25 单独表现反超 RRF？
在 Benchmark v1 中：
- BM25: Recall@1 = 92.5%, MRR = 1.0000, nDCG = 0.9964
- RRF: Recall@1 = 87.5%, MRR = 0.9750, nDCG = 0.9797

**深入根因分析（以 Q16 为例）**：
- Q16：“在业务高峰期，网关如果遇到连接数耗尽且等待排队队列溢出的极端情况会采取什么保护手段？”
- 正确答案分块为“网关连接池配置”（包含 `min_idle`, `max_connections`, 背压告警）。
- **BM25 表现**：因字面完全重合“连接数耗尽”、“等待排队队列溢出”，BM25 极其果断地给出了 **Rank 1**。
- **Dense 表现**：Dense 在语义向量空间中，由于“业务高峰期”、“极端情况”、“保护手段”等泛化词，被“高可用三态熔断器”分块的通用降级概念所误导，产生了语义漂移（Semantic Drift），将真正目标排在了 **Rank 3**，而将熔断分块排在 Rank 1。
- **RRF 融合时的“稀释惩罚”**：
  - RRF 采用无量纲倒数加权公式：$S = \frac{1}{60 + r_{\text{dense}}} + \frac{1}{60 + r_{\text{bm25}}}$。
  - 熔断分块（干扰项）：Dense 排名第 1，BM25 排名第 2，得分 = $\frac{1}{61} + \frac{1}{62} \approx 0.03252$。
  - 正确分块（真目标）：Dense 排名第 3，BM25 排名第 1，得分 = $\frac{1}{63} + \frac{1}{61} \approx 0.03226$。
  - **结果 $0.03252 > 0.03226$**！RRF 机制因为 Dense 端的高排误报，硬生生把 BM25 的第一名拉踩到了第 2 名！
- **科学启示**：在缺乏置信度校准的前提下，无脑等权 RRF 会在单路高度确信而另一路产生语义漂移时出现“负向稀释”。

### 2. 为什么 Reranker 的 nDCG 提升看起来微乎其微？
- Benchmark v1 中，BM25 的基线 nDCG 已经高达 **0.9964**（99.64%）。
- 在基线几乎打满天花板的情况下，Reranker 得到的 **0.9972** 仅提升了 0.0008（0.08%）。
- **原因**：语料太小且缺乏“高词面重合但事实完全错误”的 **强对抗负样本 (Hard Negatives)**。没有足够的困难陷阱让 BM25 翻车，就显现不出 Cross-Encoder 深度语意交叉注意力的价值。

### 3. 当前是否有足够证据证明“混合检索优于单路检索”？
- **实事求是的回答：绝对没有！**
- 基于当前的 Benchmark v1 数据，甚至可以得出“单跑 BM25 延迟最低（0.37ms）且指标最好”的相反结论。
- 如果将 Benchmark v1 包装为最终成果写在简历上，一旦面试官深究“既然 BM25 指标比 RRF 还高，你为什么还要做 Hybrid Retrieval？”将直接面临逻辑破绽。
- **必须扩容真实语料规模并引入 Hard Negatives，才能科学、客观地证明系统引入 RRF 与 Reranker 的工程必要性。**

## 五、Benchmark v2 扩容体系设计方案

为彻底打破评测饱和，建立经得起最严苛检验的工业级基准，设计 Benchmark v2：

### 1. 扩容规模规划

```text
+-----------------------+-----------------------+-----------------------+
| 维度                  | Benchmark v1 (当前)   | Benchmark v2 (扩容目标)|
+-----------------------+-----------------------+-----------------------+
| 测试文档数量           | 3 篇                  | 12 ~ 15 篇            |
| 语料涵盖领域           | 网关通信、熔断、安全合规| 涵盖分布式存储、消息队列、|
|                       |                       | 容器编排、数据库高可用等|
| 真实生成 Chunk 数量   | 16 个                 | 350 ~ 450 个          |
| 候选池 (Candidate)    | Top-20 (占比 100%)    | Top-30 (占比 ~7.5%)   |
| 最终评估 Top-K        | Top-10                | Top-10 / Top-5 / Top-1|
| 标注测试问答集         | 20 条                 | 80 ~ 100 条           |
+-----------------------+-----------------------+-----------------------+
```

### 2. 6 大靶向评测场景与设计意图

1. **Hard Negatives 强干扰对抗场景 (20 题)**：
   - *设计*：针对“超时配置”，文档 A 介绍 Redis 客户端超时（2000ms），文档 B 介绍网关接口超时（5000ms），文档 C 介绍数据库获取连接超时（3000ms）。
   - *意图*：提问“网关调用下游模型的最大超时时限是多少”。此时三篇文档均高度匹配“超时”、“配置”、“ms”关键词，BM25 极易出现关键词混淆，专门考察 Reranker 能否识别主语限定词。
2. **Zero-Lexical 纯同义语义表述场景 (15 题)**：
   - *设计*：提问完全使用口语化、抽象同义词，与文档正文零字面重合（例如：“当服务器流量过大把系统打爆前，有哪些自我保护措施”）。
   - *意图*：使 BM25 字面匹配彻底哑火（BM25 零命中），检验 Dense 语义向量检索的兜底能力。
3. **精细数值与下划线专有代号 (15 题)**：
   - *设计*：考察 `min_idle`, `acquire_timeout_ms`, `RS256`, `WORM`, `AES-256-GCM` 等高精密度工程参数。
   - *意图*：检验 `TechnicalBM25Tokenizer` 分词器在技术混合符号下的切词命中力。
4. **跨章节多事实联合召回 (15 题)**：
   - *设计*：一个问题需要同时结合来自第 1 篇规范和第 3 篇规范的 2~3 个分块才能完整作答。
   - *意图*：检验 Recall@5、Recall@10 在多目标情况下的综合召回能力。
5. **不可回答 / 域外拒绝场景 (10 题)**：
   - *设计*：包含完全无关问题（如天文、娱乐）以及近似领域但文档未记载的诱导问题（如“网关是否支持 GraphQL 订阅”）。
   - *意图*：建立“低分拒答率”评估，防止系统强行检索不相干分块。
6. **历史基线回归集合 (20 题)**：
   - 完整保留 Benchmark v1 的 20 条题目，打上 `subset: "v1_regression"` 标签，确保历史实验对比可追溯。

### 3. 数据生命周期与标注质量控制

- 每条样本增加元数据字段：
  ```json
  {
    "id": "V2-HN-01",
    "version": "2.0",
    "subset": "hard_negative",
    "status": "approved", // "approved" (已人工复核通过) | "pending" (待复核，评测时自动剔除)
    "query": "...",
    "ground_truth": "...",
    "target_chunks": [
      { "doc_name": "...", "page_number": 3, "chunk_index": 1, "relevance": 2 },
      { "doc_name": "...", "page_number": 2, "chunk_index": 2, "relevance": 0, "is_hard_negative": true }
    ]
  }
  ```
- 严格遵循：**未完成人工标注复核的样本标为 `status: "pending"`，严禁计入正式评测指标。**

## 六、当前指标计算与评测代码的问题清单及整改方案

| 编号 | 当前代码问题 | 影响后果 | 最小整改方案 |
| :---: | :--- | :--- | :--- |
| **P1** | **Precision@5 分母固定导致小样本失真** | 当黄金分块为 1 个时，理论最大 Precision 仅为 20%，拉低整体表现。 | 保持现有 Precision 计算，但在报告中补充引入 **R-Precision**（$K = \|G\|$）或 **HitRate@K**（是否命中至少 1 个）。 |
| **P2** | **耗时统计未拆分各子阶段** | Reranker 耗时（1333ms）包含了初筛时间与重排时间，且没有分离 Embedding 时间。 | 在 `run_retrieval_ablation.py` 中独立记录并输出：`dense_time`, `bm25_time`, `rrf_time`, `rerank_inference_time`。 |
| **P3** | **缺乏多候选池敏感度对比** | 候选池固定为 20，无法分析 Candidate Pool 为 10、30、50 时对延迟和召回的影响。 | 在 Runner 中增加参数控制，支持在 Benchmark v2 中对比 Pool=20 vs Pool=50。 |
