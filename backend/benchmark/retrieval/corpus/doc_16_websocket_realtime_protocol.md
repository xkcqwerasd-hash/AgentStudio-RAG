# 全双工通信与 WebSocket 实时连接治理规范

## 1. 全双工长连接应用场景与架构选型
在智能体执行复杂多步推理或涉及人机协同交互（Human-in-the-Loop）的高阶业务场景中，传统的 HTTP 单向请求响应模式无法满足双向低延迟数据交换需求。
系统在常规 Server-Sent Events (SSE) 之外，支持通过 WebSocket 协议构建全双工持久化长连接通道。
WebSocket 基于单次 HTTP/1.1 握手（带有 `Upgrade: websocket` 头）平滑升级为标准的双向 TCP 长连接，在网关层通过特有的连接池维持连接心跳；
客户端不仅可以实时接收服务端下发的 Token 流与状态机流，还能在不中断当前连接的前提下，实时向正在思考中的 Agent 注入补充约束或修改检索条件。

## 2. 心跳保活与连接空闲超时治理（PING/PONG）
由于公网与企业内网中存在大量的四层负载均衡器、NAT 网关及防火墙设备，长时间没有数据流动的无声 TCP 连接会被中间网络设备强行 RST 静默切断。
系统在 WebSocket 协议层内嵌了双向保活心跳机制：
服务端与前端客户端之间协商每隔 10 秒固定发送一个轻量级的 PING 心跳帧，接收端必须在 3 秒之内响应对应的 PONG 帧；
如果连续 2 次（即 20 秒）未收到客户端响应，或连接持续处于空闲状态超过最大空闲阈值（默认 300 秒），网关判定该客户端已发生假死或掉线，主动调用 `close(code=1001)` 优雅断开连接并回收相关套接字文件描述符。

## 3. 客户端断线自动重连与退避算法
在移动办公或弱网环境下，终端客户端的网络切网与瞬时抖动难以避免。
前端 WebSocket 客户端内嵌了基于随机扰动的指数退避重连算法（Exponential Backoff with Full Jitter）。
当检测到连接非正常中断（`event.code != 1000`）时，客户端并不发起高频连续重连，而是依据公式计算重连等待时间：
$$t_{	ext{wait}} = \min(t_{	ext{max}}, t_{	ext{base}} 	imes 2^{	ext{retry\_count}}) \pm 	ext{random\_jitter}$$
其中初始退避时间基数为 500 毫秒，最大退避上限限制为 30 秒。
通过随机打散数千个并发断线客户端的重试时刻，彻底消除了服务端重启后可能面临的“雷鸣蜂拥”（Thundering Herd）冲击。

## 4. 会话恢复与断点补发机制
为了避免因网络短暂秒断导致用户正在接收的思考链输出丢失，系统在应用层构建了轻量级的流式序号重放缓冲区。
服务端下发的每个流式数据包均自增携带连续递增的唯一消息序列号（Sequence Number, `seq`），服务端在内存循环队列中为当前会话缓存最近 50 个数据包；
当客户端在 15 秒内快速完成重连后，可以在握手消息中携带自身最后成功收到的序号（例如 `last_seq = 28`），服务端自动从该断点后按序补发丢失的报文，实现用户视觉层面的无感平滑续接。

## 5. 长连接集群与分布式 Pub/Sub 网关分发
当系统后端扩展至多台应用服务器容器形成负载均衡集群时，同一个用户的多次请求可能被分散路由，而 WebSocket 客户端仅在其中某台特定实例上保持物理连接。
系统依托 Redis 高可用集群的发布/订阅（Pub/Sub）机制构建分布式连接协同总线。
当后台异步任务或跨微服务事件需要向某用户推送消息时，发布者只需将消息广播至统一的通道 `channel:user:{user_id}`；
持有该用户真实 WebSocket 物理连接的目标应用节点订阅到该消息后，负责执行最终的底层网络帧写入，实现了与后端计算节点的完全解耦。
