# PostgreSQL 数据库架构与连接池调优指南

## 1. 异步数据库连接池参数精细调优
系统后端采用 SQLAlchemy 2.0 异步引擎配合 asyncpg 驱动与 PostgreSQL 数据库交互，连接池参数配置直接决定系统的抗压吞吐能力。
在生产环境标准性能调优实践中，单节点应用服务的连接池关键参数严格设定如下：
- `maximum_pool_size`（最大活跃连接数）：严格设定为 50，防止过多数据库后端进程产生过度的 CPU 线程上下文切换开销；
- `minimum_idle`（最小常驻空闲连接数）：设定为 10，保证在系统低谷期也能维持基本连接，避免突发流量到达时遭遇耗时的 TCP 三次握手建连；
- `connection_timeout_ms`（获取连接最长超时时间）：配置为 30000 毫秒（即 30 秒），防止客户端在连接池耗尽时无限期挂起等待；
- `idle_timeout_ms`（空闲连接回收时间）：设定为 600000 毫秒（10 分钟），超过该空闲时长的多余连接将被主动释放退还给数据库。

## 2. 核心索引设计原则与 GIN 倒排索引
数据库表索引设计严格依据查询模式区分 B-Tree 索引与 GIN（Generalized Inverted Index）广义倒排索引的适用边界。
对于主键 UUID、文档外键 `document_id`、知识库外键 `knowledge_base_id` 以及时间戳字段，一律建立标准的 B-Tree 单列或联合索引，满足等值精确过滤与时间倒序排列。
对于包含切片文本内容的全文检索字段及存储半结构化元数据的 `extra_metadata_json` JSONB 字段，系统强制采用 GIN 索引。
GIN 索引允许对 JSONB 文档内部任意深度的属性键值和数组元素进行极速包含查询（`@>` 操作符），其检索效率相比全表 JSON 扫描提升两个数量级。

## 3. 慢查询审计与自动化告警机制
为保障在线交互式对话的极速响应，数据库层配置了严密的慢查询（Slow Query）监控与审计规范。
系统在数据库配置文件 `postgresql.conf` 中开启 `log_min_duration_statement = 200`，即所有执行耗时超过 200 毫秒的 SQL 语句将被统一记录至慢查询日志。
监控代理模块实时分析数据库日志流，一旦某类慢查询在 5 分钟内连续出现超过 10 次，立即向技术保障群推送包含具体执行 SQL 的告警通知。
研发人员通过在调试环境中结合 `EXPLAIN (ANALYZE, BUFFERS)` 执行计划，精准定位是因全表顺序扫描（Seq Scan）还是临时磁盘排序（External Sort Disk）导致的慢查询。

## 4. 主从流复制架构与读写分离规范
系统部署采用一主一从（Primary-Standby）的 PostgreSQL 高可用集群架构，依托内置的物理流复制（Streaming Replication）保持数据近实时同步。
业务读写遵循明确的读写分离规范：所有包含数据写入、更新与删除的事务（如上传新文档、删除知识库、插入聊天消息）必须路由至主库执行。
所有无事务要求的纯读取高频请求（如列表翻页、历史消息翻查、切片详情查看）分流至只读从库。
主从流复制监控组件实时检测从库复制延迟（Replication Lag），若主从延迟超过 1000 毫秒阈值，系统自动触发写穿透保护，临时将所有关键读请求全部回切至主库，杜绝读到脏旧数据。

## 5. MVCC 多版本并发控制与事务隔离
PostgreSQL 底层依赖 MVCC（Multi-Version Concurrency Control）机制实现读不阻塞写、写不阻塞读的高并发能力。
系统业务会话统一采用标准读已提交（Read Committed）事务隔离级别，在避免不可重复读性能损耗的同时完全规避脏读（Dirty Read）现象。
为防止并发写入同一文档切片引发死锁，系统制定了严格的单向加锁顺序规范：在执行多切片批量修改前，代码层必须按切片主键 `chunk_id` 进行字典序全局排序后再逐行加锁。
系统定期执行后台自动维护（Autovacuum），及时清理因 UPDATE 和 DELETE 产生的死元组（Dead Tuples），防止表膨胀（Table Bloat）。
