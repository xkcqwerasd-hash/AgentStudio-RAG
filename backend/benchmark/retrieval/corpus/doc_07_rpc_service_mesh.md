# RPC 远程通信与服务网格治理规范

## 1. gRPC 多路复用与二进制高效序列化
在微服务内部节点间高频交互场景下，传统的 HTTP/1.1 JSON 传输协议存在严重的文本解析慢与队头阻塞（Head-of-Line Blocking）性能瓶颈。
系统核心微服务间通信统一采用基于 HTTP/2 协议底层的 gRPC 远程过程调用框架。
依托 HTTP/2 的多路复用（Multiplexing）特性，单个持久化 TCP 长连接能够并发承载上千个双向并行的 RPC 数据流（Streams），大幅减少连接频繁创建销毁的资源开销。
数据传输严格采用 Protocol Buffers (Protobuf v3) 二进制序列化，相比冗余的 JSON 字符串体积缩减 60% 以上，序列化与反序列化 CPU 耗时降低至三分之一。

## 2. 负载均衡策略演化与最小活跃连接
服务调用客户端内置智能负载均衡器，支持依据下游微服务的具体业务特征配置差异化的负载分发策略。
对于纯无状态的高速计算服务，系统默认使用加权轮询算法（Weighted Round Robin），依据物理机配置规格按比例分配请求。
对于涉及长耗时大模型交互或复杂查询的微服务，系统强制采用平滑最小活跃连接数算法（Least Active Connections）。
该算法实时统计每个下游节点当前尚未完成的未决请求数（Pending Requests），优先将新请求派发给当前并发任务最少的节点，有效消除因长尾请求导致的个别实例过载问题。

## 3. 服务注册中心与心跳摘除生命周期
微服务拓扑状态由分布式服务注册中心（Service Registry）集中统一维护。
所有服务实例在引导启动就绪后，主动向注册中心注册自身 IP 地址、监听端口及环境元数据，并启动后台守护协程以固定 5 秒周期向注册中心上报存活心跳。
注册中心为每个服务实例维护租约倒计时：若某个实例因物理断电或死锁连续 3 次心跳丢失（即超过 15 秒未上报心跳），注册中心立刻将该实例标记为不健康状态并将其从可用服务实例列表中物理摘除。
服务变更事件通过长轮询与推送机制在 1 秒内同步给所有客户端本地注册表缓存。

## 4. 重试风暴防范与全局重试预算（Retry Budget）
在分布式网络遭遇瞬时局部闪断或下游依赖服务性能退化时，盲目的客户端调用重试极易成倍放大系统整体流量，形成毁灭性的重试风暴（Retry Storm）。
系统在 RPC 框架层制定了严密的重试配额控制规范：
- 调用链路限制：在整个分布式调用链路深度上，一次原始用户请求仅允许在叶子节点处最多重试 1 次，严禁链路层层嵌套重试；
- 状态码限制：仅对明确返回为网络连接超时或目标服务不可达的特定状态码执行重试，业务逻辑错误绝对禁止重试；
- 全局重试预算（Retry Budget）：客户端本地维护滑动窗口重试统计，重试请求在总请求量中的占比严禁突破 10% 的硬上限，一旦重试率达到 10% 则就地熔断不再重试。

## 5. 服务网格 Sidecar 资源限制与性能指标
在基于 Istio / Envoy 构建的服务网格（Service Mesh）生产架构中，网络流量由与业务容器同 Pod 伴生部署的 Envoy Sidecar 代理进行全透明劫持。
为防止 Sidecar 容器自身反向争抢业务处理的计算资源，系统对单个 Sidecar 容器配置了硬性资源配额限制：CPU 资源配额上限限制为 2 核，常驻物理内存上限限制为 1GB。
网络代理转发性能遵循严格的低延迟 SLA 指标：单个 Envoy 代理在处理一跳流量转发时引入的平均网络延迟必须严格控制在 2 毫秒以内（P99 延迟不超过 5 毫秒）。
