# 分布式链路追踪与可观测性体系规范

## 1. OpenTelemetry 标准与跨线程 TraceId 透传
在复杂微服务网格与长流程 Agent 异步调用系统中，单个用户提问往往涉及数十次微服务调用与多步工具执行，定位性能瓶颈必须依赖全链路追踪技术。
系统遵循云原生计算基金会（CNCF）的 OpenTelemetry 工业标准构建端到端可观测性基础设施。
系统在网关接收到初始请求的一瞬间，生成全局唯一的 128 位十六进制字符串作为 `TraceId`，并为当前操作段分配 64 位 `SpanId`。
该追踪上下文依据 W3C Trace Context 规范封装为标准 HTTP 头 `traceparent`，在微服务跨网络调用、异步线程池切换以及消息队列生产消费全链路中强制透传。

## 2. 动态采样率配置与尾部采样策略（Tail-based Sampling）
全量采集分布式调用链路数据在海量请求场景下会产生巨大的网络传输带宽与底层存储开销。
系统实施头部概率采样（Head-based）与尾部智能采样（Tail-based）相结合的混合采样策略。
在默认稳定生产环境中，系统对常规正常的 HTTP 请求执行 5% 的低比例概率采样，保证监控数据的宏观统计代表性；
在后端追踪收集器端配置尾部采样规则：所有执行结果标记为错误（包含 HTTP 5xx 状态码或捕获到未处理异常）的链路，以及总响应耗时超过 1000 毫秒的慢调用链路，自动执行 100% 强制完整保存，杜绝故障样本丢失。

## 3. Prometheus 四大黄金监控指标规范
系统在微服务各通信组件与应用层统一埋点暴露符合 Prometheus 标准规范的监控指标（Metrics）。
监控大盘严格围绕 Google SRE 提出的四大黄金监控指标（The Four Golden Signals）组织：
- 延迟（Latency）：度量请求处理耗时，系统采用高精度直方图（Histogram）统计，划分为 10ms、50ms、200ms、1000ms 等不同 Bucket；
- 流量（Traffic）：度量系统当前的实际吞吐负荷，通过 Counter 类型计数器记录每秒的请求总数 QPS；
- 错误（Errors）：度量显式失败请求的速率，精确区分客户端 4xx 错误与服务端 5xx 系统崩溃错误；
- 饱和度（Saturation）：度量系统计算资源的繁忙程度，记录 CPU 利用率、JVM 堆内存占比以及数据库连接池排队率。

## 4. 结构化日志规范与 Trace 自动关联
所有微服务与组件统一采用 JSON 格式进行标准结构化日志输出，坚决禁止无格式的凌乱纯文本控制台打印。
日志框架在输出每行日志前，自动从当前执行上下文（MDC / ContextVars）中抓取当前的 `trace_id`、`span_id`、`user_id` 与 `tenant_id` 并作为顶层 JSON 字段直接输出。
集中式日志收集组件（如 Vector / Fluentbit）将结构化日志流实时汇聚至日志中心，运维人员在排障时只需在控制台输入单个 `trace_id`，即可一键检索出该次请求在所有微服务节点上打印的全部上下文日志。

## 5. 告警阈值分级与事件风暴抑制规范
为了防止突发网络抖动导致技术运维人员遭遇海量短信与邮件轰炸，监控告警系统设计了严格的分级与降噪抑制机制。
系统将告警级别划分为两级：P1 紧急告警（核心业务宕机或错误率超过 15%）与 P2 预警告警（P95 延迟微幅升高或连接池利用率超过 70%）。
监控规则配置防抖滤波：只有在连续 3 次检测周期（每次检测周期为 1 分钟）内指标均突破阈值时，才会真正触发告警外发。
系统内嵌告警收敛引擎，在相同的故障服务范围内，对同类告警自动开启 15 分钟的静默冷却期，有效抑制次生告警风暴。
