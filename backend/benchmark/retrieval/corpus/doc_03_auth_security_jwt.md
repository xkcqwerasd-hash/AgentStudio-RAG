# 微服务鉴权体系与 JWT 令牌管理规范

## 1. 无状态身份认证与 RS256 签名机制
企业级微服务系统采用基于标准 JSON Web Token (JWT) 的无状态身份认证机制，实现前端客户端与后端多微服务之间的高性能安全通信。
为杜绝对称加密密钥在多微服务节点之间下发共享引发的安全泄露风险，系统统一强制使用基于非对称加密算法的 RS256（RSA Signature with SHA-256）进行令牌签名。
统一认证中心在用户登录成功后使用私钥对 JWT 进行签名签发，微服务网关和业务微服务仅持有公钥以执行本地高速验签，彻底解耦认证流程。
JWT 令牌由 Header（头部）、Payload（载荷声明）与 Signature（签名串）三段组成，载荷中包含脱敏的用户唯一标识 user_id、租户标识 tenant_id 及角色列表 roles。

## 2. 令牌时效与双 Token 自动续期方案
系统实施安全且兼顾用户体验的双 Token 认证策略（Dual-Token Strategy）。
其中，用于访问日常业务接口的 Access Token 设置了严格的短期时效，默认有效周期为 72 小时（3 天）。
为避免用户在 Access Token 过期后频繁被迫重新输入用户名密码登录，系统同时签发一个具备高强度随机熵的 Refresh Token，其生命周期设定为 7 天。
当客户端调用接口收到 HTTP 401 令牌过期错误时，自动在后台携带 Refresh Token 访问刷新端点获取新的 Access Token；若 Refresh Token 本身超过 7 天过期，则强制引导用户重新登录。

## 3. 分布式令牌黑名单与 Redis 协同存储
尽管无状态 JWT 在默认情况下无需依赖中心化存储，但在用户主动登出、修改密码或管理员执行封禁踢下线等紧急安全事件中，必须具备主动注销失效的能力。
系统在 Redis 高可用集群中构建了高性能分布式令牌黑名单（Token Blacklist）。
当用户触发注销操作时，网关提取该 Access Token 中的全局唯一 JWT 标识符 jti（JWT ID），将其作为 Key 写入 Redis 黑名单，Value 设为封禁时间戳。
该黑名单键的生存时间（TTL）被精确设置为该 JWT 的剩余有效时间，一旦令牌自然到期，Redis 自动驱逐该键，保障黑名单占用的内存空间不会持续膨胀。

## 4. 传输层安全与 TLS 1.3 证书卸载
网关对外通信链路强制开启传输层安全加密协议 TLS 1.3，全面禁用存在安全缺陷的 SSLv3、TLS 1.0 与 TLS 1.1 老旧协议。
系统采用 ECDSA（椭圆曲线数字签名算法）与 RSA 2048 双证书自适应握手机制，优先协商前向安全性更高、计算延迟更低的 ECDHE-ECDSA 密钥交换套件。
在系统物理网络拓扑中，网关在边缘入口层统一执行端到端证书卸载（TLS Termination），解密后的流量在受严格物理安全防护的内部私有局域虚拟子网（VPC）中流转。
对于涉及金融级别高敏感业务模块的跨机房专线调用，内部服务间强制启用基于 mTLS（双向双向认证）的私有 CA 证书验证。

## 5. 多租户数据隔离与上下文透传规范
在企业级多租户 SaaS 部署架构下，系统通过在网关层提取用户 JWT 中的 `tenant_id` 实现严格的逻辑隔离。
网关在验签通过后，将用户身份及租户元数据注入下游 HTTP 协议头的标准字段 `X-Tenant-Id` 与 `X-User-Id` 中。
下游所有业务微服务与数据库 ORM 层拦截器在执行 SQL 增删改查时，自动附加 `WHERE tenant_id = :current_tenant` 过滤约束，杜绝越权访问其他组织的数据。
在异步线程与分布式 RPC 调用链路中，系统通过 ThreadLocal 与微服务上下文透传机制保证 `tenant_id` 不丢失。
