# 系统对抗干扰与对照控制语料库

## 1. 数据库连接池与网关连接池同名参数混淆
在微服务系统整体架构中，存在多个在不同物理层级独立运行的连接池组件，其核心参数名称完全相同，极易对基于关键词检索的算法产生严重混淆干扰。
例如，在后台关系型数据库 PostgreSQL 的连接池调优实践中，数据库访问组件同样定义了最小空闲连接数 min_idle。
然而，数据库连接池的 min_idle 被严格设定为 10，其最大容量 maximum_pool_size 设定为 50，专门用于管理与数据库 5432 端口的 TCP 会话复用；
相比之下，微服务网关入口层的连接池 min_idle 同样为 10，但其最大连接数 max_connections 设定为 100，管理的是面向下游微服务的 HTTP 代理长连接。
如果检索系统无法识别“网关”与“数据库”的上下文语境，极易在此类参数查询上发生召回偏差。

## 2. 消息队列超时参数与接口超时参数对照
在异步事件驱动架构中，分布式消息队列（如 Apache Kafka）与网关通信接口均存在名为“超时”的参数设置，但两者的数值与异常语义存在巨大反差。
Kafka 消费者集群的核心健康保活参数配置为 `session.timeout.ms = 45000`（即 45 秒），用于判定消费者实例是否发生崩溃或发生长 GC 停顿；
而微服务网关入口对下游 HTTP 请求设定的全局调用超时阈值严格配置为 5000 毫秒（即 5 秒），超时抛出的是 504 Gateway Timeout 状态码；
此外，Redis 互斥锁 RedLock 的自动持有锁超时被配置为 10 秒。
检索算法若单纯匹配“超时”或“timeout”，必须依靠深层上下文来区分究竟是消息队列的 45 秒、网关调用的 5 秒还是分布式锁的 10 秒。

## 3. 硬件加密芯片方案与软件 Fernet 架构对比
在企业底层基础设施建设方案中，存在使用专用物理硬件安全模块（Hardware Security Module, HSM）的高速加密芯片方案。
该物理芯片加速方案采用 AES-256-GCM 算法并在专用硬件加密卡中直接运算，宣称具备每秒数万次的极高加密吞吐量；
然而，在 AgentStudio-RAG 当前纯软件运行时的实际实现中，系统并未依赖任何外部专有硬件加密卡，而是基于标准的 Python cryptography 库实现了纯软件级的 Fernet 加密方案；
Fernet 底层固定采用 AES-128-CBC 加密配合 HMAC-SHA256 签名，其密钥长度为 128 位而非 256 位。
两种加密方案在技术架构、算法实现与硬件依赖上形成强烈的概念对照，用于测试检索模型在面对高相似度安全专业名词时的鉴别精度。

## 4. 客户端交互防抖与后端三态熔断时间尺度混淆
在前端用户交互与后端微服务高可用机制中，均存在“冷静/延迟”机制，但两者的时间尺度与应用场景截然不同。
在前端网页输入框（ChatComposer）交互优化中，为了防止用户快速打字触发高频无意义的自动联想请求，前端 JavaScript 代码设置了轻量级的防抖时间（Debounce Time），其数值通常设定为 300 毫秒；
而在后端微服务容灾机制中，三态熔断器在触发完全打开（OPEN）状态后，所强制进入的冷静恢复等待期被配置为整整 60 秒；
两者的参数单位一个是毫秒（300ms），一个是秒（60s）。
当用户提出类似“系统设置的冷静期是多少”等模糊表达时，检索系统必须准确识别用户提问的核心意图是指前端组件的防抖还是后端的熔断冷静期。

## 5. 非核心通知服务的伪熔断丢弃策略
并非系统中的所有微服务调用都遵循严格的 CLOSED / OPEN / HALF_OPEN 三态熔断器机制。
对于运营短信推送、站内营销弹窗等非关键通知类旁路微服务，系统为了极简化开销，并未挂载复杂的三态熔断状态机，而是采取了极简的“快速静默丢弃”（Silent Drop）策略；
当通知微服务不可用或抛出异常时，调用方仅在日志中打印一条 WARN 警告后便直接忽略返回成功，既不触发滑动时间窗口统计，也不进入冷静恢复期；
这种旁路丢弃策略与核心业务链路中具备严格自愈机制的三态熔断器形成了强烈的架构反差，专门用于检验复杂多文档综合问答时的防误导能力。

## 6. 网关 502 Bad Gateway 与 504 Gateway Timeout 区分
在网关错误码体系中，HTTP 502 与 HTTP 504 经常容易被混为一谈。
网关抛出 HTTP 502 Bad Gateway 的真实原因是：网关在尝试与下游微服务建立 TCP 连接时遭遇对方直接拒绝（Connection Refused），或者下游服务在处理过程中由于 OOM 发生崩溃导致连接被意外重置（Connection Reset by Peer）；
而网关抛出 HTTP 504 Gateway Timeout 的真实原因是：TCP 连接已成功建立，但下游服务在超过了 5000 毫秒的全局调用超时时间内未完成业务计算，网关主动掐断连接；
两者代表了完全不同的网络故障机理，要求检索模型能够在面对细微错误码语义差异时保持绝对的技术敏感度。
