# Redis 分布式缓存架构与三防治理规范

## 1. 缓存穿透防御体系与布隆过滤器
在企业级智能问答场景下，当高频查询请求访问数据库中根本不存在的非法知识库 ID 或文档 ID 时，容易导致请求直接穿透缓存击溃后端数据库。
系统设计了由布隆过滤器（BloomFilter）与空对象缓存构成的双层穿透防御体系。
在网关和查询层前置布隆过滤器，对全量已存在的知识库 ID 计算 3 个独立哈希函数并映射到固定位图（BitMap）中，误报率严格控制在 0.01% 以下。
若布隆过滤器判定某 ID 必不存在，则在毫秒级内直接阻断请求；对于穿透布隆过滤器并在数据库中查空的请求，系统在 Redis 中缓存一个特殊的空对象标识 `__NULL__`，其超时失效时间（TTL）强制设定为 60 秒，有效防御同参数的高频恶意扫库。

## 2. 缓存击穿与 RedLock 互斥锁机制
当某个极高热度的知识库元数据或全局配置的缓存恰好在某一秒到期失效，同时有数百并发请求涌入时，容易发生大量请求瞬间涌入数据库的缓存击穿问题。
系统采用基于 RedLock 算法的分布式互斥锁解决击穿隐患。
当线程发现热点缓存未命中时，并不立刻查询数据库，而是尝试向 Redis 申请互斥排他锁（Key 格式为 `lock:kb:{kb_id}`），设置锁超时保护为 10 秒。
仅有成功获得互斥锁的 1 个线程执行数据库读取并重新刷新 Redis 缓存；未抢到锁的其余并发线程执行 50ms 纳秒级休眠并重试读取缓存，从而将数据库并发压力严格压缩至 1 次。

## 3. 缓存雪崩与过期时间随机抖动（Jitter）
当海量知识库切片的缓存被配置为相同的固定过期时间时，极易在某一时间点集中并发过期，导致瞬时数据库负载陡增发生缓存雪崩（Cache Avalanche）。
系统制定了严格的缓存键过期时间随机扰动策略（Jitter Strategy）。
系统禁止在业务代码中写入静态固定过期间隔，所有缓存写入操作在基础有效期（如 3600 秒）的基础上，必须通过均匀随机函数追加一个 1 到 300 秒之间的随机偏移量（`random.randint(1, 300)`）。
通过离散化不同键的失效时间戳，系统将原本尖锐的过期峰值平滑抹平为连续分布的平缓曲线，彻底消除集中过期引发的数据库抖动。

## 4. 内存淘汰策略与容量规划规范
Redis 实例内存容量并非无限，当业务数据持续写入达到预设的最大内存配额 `maxmemory` 时，必须执行确定性的内存淘汰机制。
系统配置生产环境 Redis 的内存淘汰策略为 `volatile-lru`（即优先在设置了过期时间的键集合中，淘汰最近最少使用的冷门键）。
系统严禁配置默认的 `noeviction` 策略，防止在内存耗尽时拒绝新的写入操作导致前端会话状态无法保存。
运维监控对 Redis 内存占用率设置 80% 黄色告警线与 90% 红色扩容线，当内存利用率突破 80% 时自动触发冷门临时附件缓存的清理工作。

## 5. Redis Sentinel 哨兵模式与故障自动转移
生产环境 Redis 采用由 1 主 2 从加 3 哨兵节点组成的 Sentinel 高可用集群架构。
3 个独立的哨兵节点（Sentinel）通过每隔 1 秒向主节点发送 PING 心跳，持续监控主节点存活状态。
当有 2 个哨兵（达到仲裁法定人数 Quorum=2）判定主节点发生客观下线（Objectively Down）时，哨兵集群在 15 秒之内自动完成新主节点的选举与故障倒换（Failover）。
应用程序中的 Redis 客户端监听 Sentinel 的变更广播通知，实时动态更新写入节点连接池，保证缓存读写在故障切换过程中仅发生亚秒级瞬时微抖动。
