# 多轮对话查询重写与上下文指代消解规范

## 1. 多轮对话中的语义漂移与指代鸿沟
在真实的连续智能问答场景中，人类用户极少在每次提问中重复输入冗长完整的背景主语，而是大量使用代词、省略或增量追问。
例如，用户在上一轮提问“微服务网关的连接池参数是多少？”，在下一轮紧接着提问“那么它的超时时间呢？”或“如果发生卡顿怎么处理？”。
若直接将包含代词“它”或省略主语的原始提问直接送入向量检索或 BM25 检索，检索模型由于缺失“微服务网关”这一核心主语，必然召回毫无关联的其他组件文档，发生严重的语义漂移。
为此，系统在检索流水线的最前置环节引入了多轮查询重写器 QueryRewriter（定义于 `app/rag/query_rewriter.py`）。

## 2. QueryRewriter 系统指令设计与原则
QueryRewriter 依托单轮轻量级大模型调用实现精准的上下文语义补全，其内置系统提示词遵循严格的企业级重写原则：
1. 信息补全：仅补充当前提问缺失的关键限定词（如将“那么它的超时时间呢？”改写为“微服务网关针对下游接口调用的超时限制是多少毫秒？”）；
2. 指代消解：将模糊的代词（如“它”、“这个”、“前一个状态”）精准替换为前文提及的具体客观实体；
3. 无关问题零干扰：当用户突然发起与前文毫无关系的全新独立提问时（如突然问“Python 怎么安装？”），系统严禁强行拼接历史背景，保持原句不变并将 `is_rewritten` 标记为 `false`；
4. 严格禁止直接回答：提示词严厉禁止重写模型尝试解答问题，重写模型必须且仅能输出重写后的检索关键词。

## 3. 结构化 JSON 强约束输出规范
为防止大模型输出冗余的寒暄问候或思考过程导致下游解析崩溃，QueryRewriter 要求模型必须以标准单行 JSON 格式响应：
```json
{
  "is_rewritten": true,
  "rewritten_query": "微服务网关接口调用的全局调用超时时间是多少毫秒？",
  "reason": "补充前文微服务网关主体并消解代词"
}
```
后端解析模块在收到模型输出后，使用鲁棒的正规表达式优先提取首个花括号匹配块，有效防御少量模型因未完全遵循约束而携带的前置 Markdown 代码块标记（如 ````json`）。
若解析成功且 `is_rewritten` 为真，检索链路将全量采用 `rewritten_query` 发起混合检索。

## 4. 超时保护与无感降级容灾机制
在快速问答模式下，查询重写属于增加在检索前方的串行步骤，如果重写模型发生网络卡顿，将直接拉长整个对话的端到端响应时间。
系统为 QueryRewriter 配置了严格的硬性调用超时参数 `QUERY_REWRITING_TIMEOUT`，默认阈值设定为 3.0 秒。
在执行重写时，逻辑包裹在 `asyncio.wait_for` 超时保护块中：
若大模型在 3.0 秒内未能返回结果，或者模型抛出网络中断、JSON 格式解析错误等任何未知异常，系统立即触发优雅降级（Fallback）；
降级逻辑将 `rewritten_query` 直接无缝重置为用户的 `original_query`，并将 `fallback = True` 写入执行轨迹日志，保证后续检索流程绝对不被阻塞。

## 5. 历史轮次裁剪与防上下文污染
在长对话会话中，数十轮前的陈旧历史与当前提问通常已无直接关联，若盲目将所有历史喂给重写器，极易发生“越改越偏”的上下文污染问题。
系统通过 `ContextBudgetManager.prune_history_for_rewriter` 在发起重写前对历史消息执行防御性修剪。
系统仅抓取最近的至多 3 轮完整问答对（即最多 6 条历史消息），总字符长度严格限制在 1000 字符以内；
超出范围的早期历史被自动舍弃，这不仅大幅压缩了重写模型的推理延迟与 Token 开销，更显著提升了对当前核心意图的捕捉聚焦度。
